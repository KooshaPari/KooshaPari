## Performance baseline (round 6k, 2026-10-19 03:21 UTC)

Captured via `curl -w` against the live 4
production domains and the key prebuilt assets.
This is **not** a Lighthouse audit (no headless
browser available; see "Lighthouse" section
above) and does not measure Core Web Vitals
(LCP, CLS, FID/INP) which require real-user
or headless-browser measurement. What it does
measure is the network-side performance that
any Lighthouse run would observe at the network
boundary: TTFB, total round-trip, response
sizes, and cache hits.

### Decomposed request timing (`curl -w`)

Primary HTML, `https://kooshapari.com/`:
- DNS lookup: 6.5 ms
- TCP connect: 21.5 ms
- TLS handshake: 39.5 ms (61.0 - 21.5)
- Pre-transfer: 61.1 ms
- TTFB (server): 89.4 ms
- Total round-trip: 90.7 ms
- Response size: 22,503 B (HTML)
- HTTP/2 200, `x-vercel-cache: HIT`

### Cold-cache + protocol-level (round 6l, 2026-10-19 03:24 UTC)

A second pass that probes what the
cached baseline hides: cold-cache paths,
forced protocol downgrades, concurrent
load, and CDN POP routing.

**Cold cache (`Cache-Control: no-cache`):**
- Sample 1: 181 ms TTFB, 182 ms total
  (first request after no-cache, no shared
  client state)
- Sample 2: 95 ms TTFB, 98 ms total
  (re-validated, back to warm)
- Sample 3: 94 ms TTFB, 94 ms total
- The 181 ms first-hit is a revalidation
  round-trip to origin; subsequent samples
  drop to 94-95 ms. Vercel's edge serves
  from local cache even when the client
  requests no-cache, so the cold-cache
  penalty is bounded.

**Cold cache (unique query param, e.g.
`?nocache=1794647316`):**
- 3 samples: 94-107 ms TTFB
- Query params do not affect cache routing
  on Vercel; this matches the 5-sample
  warm-cache median (111 ms). Confirms
  the path-based cache key is the right
  read of the system.

**Protocol downgrade (HTTP/1.1 vs HTTP/2):**
- HTTP/1.1 forced: 92-101 ms TTFB
- HTTP/2 default: 93-114 ms TTFB
- No meaningful difference. The site is
  a single HTML doc with a few small assets,
  so HTTP/2 multiplexing has nothing to
  gain. Both protocols are in the same
  90-115 ms TTFB band.

**TLS version forcing:**
- TLS 1.2 forced: 126-261 ms TTFB
  (one outlier at 261 ms, mean ~170 ms)
- TLS 1.3 forced: **0 B received**
  (`time_starttransfer=0.000000`,
  `size_download=0`). The 22-37 ms
  `time_total` is the abandoned-attempt
  window. Either the curl client on this
  host cannot complete a TLS 1.3 handshake
  with Vercel's edge, or Vercel's `sfo1`
  POP rejected the TLS 1.3 client hello
  for this path. A real browser will
  negotiate whatever it speaks best
  with the server (typically TLS 1.3
  in production); this curl baseline
  only shows that the local curl+TLS
  stack on this host does not complete
  a TLS 1.3 request to this edge. **This
  is a real signal of a client+server
  interaction; it does not prove Vercel
  lacks TLS 1.3 globally.** Production
  browsers (Chrome, Firefox, Safari) all
  use TLS 1.3 with Vercel by default.

**Concurrent load (10 parallel HTML fetches,
3 trials):**
- Trial 1: 10 reqs in 149 ms wall
  (min 92 ms, max 142 ms, mean 107 ms)
- Trial 2: 10 reqs in 123 ms wall
  (min 84 ms, max 109 ms, mean 102 ms)
- Trial 3: 10 reqs in 116 ms wall
  (min 90 ms, max 110 ms, mean 98 ms)
- All 30 responses: HTTP 200, no errors
- Connection-pool handles 10 parallel
  requests without any 429, 5xx, or
  degraded TTFB. This is the bandwidth
  a single client would see when
  refetching the home page after
  revalidation, or a script would see
  when polling. Mean TTFB stays in
  the 98-107 ms band.

**Edge POP routing (`x-vercel-id`
sampling):**
- `kooshapari.com` -> `sfo1` (5/5 samples)
- `www.kooshapari.com` -> `sfo1` (1/1)
- `kooshapari-site.vercel.app` -> `sfo1` (1/1)
- `phenotype.space` -> no `x-vercel-id` in the
  HEAD response. A direct probe on
  2026-10-19 20:54 UTC showed the reason: the
  response carries `server: cloudflare` and
  `cf-ray: ...-LAX` and **no** `x-vercel-id`.
  `phenotype.space` is a separate Cloudflare Pages
  site (title "Phenotype"), not an alias of the
  `kooshapari-site` Vercel project.
- The 3 in-scope portfolio domains route to the
  `sfo1` (San Francisco) edge. This is the
  operator's nearest POP from the test source. Real
  users from other geographies will hit their
  nearest Vercel POP and see different but
  in-the-same-envelope TTFBs.

### Summary (round 6l update)

The cold-cache / protocol-level pass
confirms the round 6k warm-cache baseline:
- TTFB stays in the 89-181 ms band
  across cold, warm, HTTP/1.1, HTTP/2,
  and 10x concurrent loads
- TLS 1.2 handshake adds ~30-90 ms over
  the TLS-cached path; TLS 1.3 is a
  client+server interaction the local
  curl cannot complete (production
  browsers will negotiate correctly)
- 10x concurrent returns 30/30 HTTP 200
  in ~120-150 ms wall (no 429s, no 5xx)
- The 3 in-scope portfolio domains route to
  Vercel's `sfo1` edge. (`phenotype.space` is
  Cloudflare, not Vercel - see the correction
  above.)
- Bundle 220,293 B (under 230 KB cap)
- HTML 22,503 B, data 12,204 B,
  prerender 13,426 B

This is the network-side reality. A
real Lighthouse run on a production
browser would observe similar TTFB
and response sizes, plus LCP, CLS,
INP, FCP, TBT metrics that this
curl-based baseline cannot capture.
